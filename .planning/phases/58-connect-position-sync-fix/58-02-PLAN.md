<objective>
Rust half of the Connect position sync fix (Part A, 58-CONTEXT.md) — the root-cause fix that makes mid-song Connect resume position correct for the first time.

Bug: on session start, `TrackChanged` None→Some sets `needs_position_sync = true` so the next `Playing` (which carries `position_ms`) can emit a `seek` to sync the LMS progress bar. But when the event sequence is TrackChanged(None→Some) → TrackChanged(Some→Some) → Playing (mid-song resume where Spirc delivers a second TrackChanged before the first Playing), the Some→Some branch unconditionally clears the flag — so the seek never fires and LMS stays at position 0.

Fix: (1) stop clearing the flag in `TrackChanged` Some→Some, preserving the pending session-start sync across the change event; (2) consume the flag in the `Playing` Some→Some (different-id) branch after emitting `change`, mirroring the existing same-id consume pattern. Safety: the flag is only ever set at session start, so normal skips are unchanged; the `secs > 1.0` guard prevents spurious seeks for tracks starting at 0.

Note: this change to `librespot-spoton/` triggers the CI binary rebuild on push. No Cargo.toml version bump — no new CLI flags or features, just a bug fix in event emission logic.

Purpose: Root-cause fix; complements but does not depend on Plan 01 (Perl hotfix).
Output: Modified `librespot-spoton/src/connect.rs`, `cargo check` clean.
</objective>
