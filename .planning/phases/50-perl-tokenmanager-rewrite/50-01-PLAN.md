<objective>
Rewrite TokenManager.pm from Keymaster-based binary spawning to PKCE-native pure Perl token
management. All token lifecycle operations (fetch, refresh, cache, error handling) use PKCE.pm
primitives — no librespot subprocess. The flavor system (own/bundled) is removed from
getToken/_cacheToken/removeAccount. Re-auth state tracking (needsReauth flag) is added for
the 4-channel notification system (D-08). Covers D-01, D-03, D-04, D-05, D-06, D-07, D-08
(Channels 3+4), D-09.

Extends PKCE.pm error callback to surface HTTP status code and OAuth error type,
enabling TokenManager to distinguish permanent revocation (invalid_grant/400) from transient
network failures (Pitfall 1 from RESEARCH.md).

Purpose: AUTH-05 — TokenManager.pm refreshes Web API tokens via standard OAuth refresh flow,
no binary spawn needed for API calls.

Output: Rewritten TokenManager.pm, extended PKCE.pm error path, rewritten test suite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| TokenManager -> Spotify Accounts API | Refresh token sent over HTTPS to accounts.spotify.com/api/token |
| TokenManager -> filesystem | Refresh tokens read/written to pkce_tokens.json (chmod 0600) |
| TokenManager -> LMS cache | Access tokens cached in-memory via Slim::Utils::Cache |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-50-01 | Information Disclosure | TokenManager.pm log output | high | mitigate | Never interpolate access_token or refresh_token into log calls. Use masked accountId (substr($accountId,0,4).'****'). Enforced by acceptance criteria + test assertions. |
| T-50-02 | Tampering | Refresh Token Rotation race | high | mitigate | Preserve H3 in-flight coalescing pattern via %_refreshInflight keyed by accountId. Only one concurrent _refreshToken call per account; additional callers queue callbacks. Prevents double-rotation that could invalidate tokens. |
| T-50-03 | Denial of Service | False re-auth notification on transient failure | medium | mitigate | Inspect PKCE.pm error callback's structured error detail for oauth_error='invalid_grant' before calling _markNeedsReauth. Transient errors (timeout, 5xx) logged but do not set the persistent reauth flag (Pitfall 1). |
| T-50-04 | Tampering | Refresh token persistence failure | high | mitigate | Use PKCE::storeTokens (atomic write-then-rename, chmod 0600). If storeTokens fails, set _markNeedsReauth('persist_failed') and still deliver the current access_token (valid ~1h) but flag the account for re-auth. |
| T-50-05 | Information Disclosure | Refresh token in LMS cache | medium | mitigate | Only access_token is stored in Slim::Utils::Cache (spoton_token_{accountId}). Refresh tokens remain exclusively in chmod-0600 pkce_tokens.json files on disk, never in the LMS cache subsystem. |
| T-50-06 | Spoofing | accountId path traversal in PKCE::loadTokens | low | accept | accountId values originate from internal call sites (Client.pm's activeAccount pref, derived from /me user ID). No HTTP request parameter flows directly into accountId. removeAccount already validates /\A[0-9a-f]{8}\z/. Risk is LOW because attack requires LMS admin access to set a malicious pref value. |
| T-50-SC | Tampering | npm/pip/cargo installs | low | accept | No package installs in this phase. All modules are LMS-bundled or Perl core. |
</threat_model>
